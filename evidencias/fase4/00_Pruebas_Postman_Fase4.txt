COMMUNITY 360 - LISTA DE PRUEBAS POSTMAN DE LA FASE 4

OBJETIVO
Validar en Render las consultas y operaciones reales de la API. Este archivo es
una lista de trabajo para tus pruebas, no el documento técnico del proyecto.
Los resultados se dejan PENDIENTES hasta que los ejecutes y conserves evidencia.

ARCHIVO PARA IMPORTAR
COMMUNITY360_Fase4_Completa.postman_collection.json (en esta misma carpeta).

PREPARACIÓN
1. En Postman Desktop: Import -> Files -> selecciona el JSON de esta carpeta.
2. Selecciona la colección "COMMUNITY 360 Fase 4 - Pruebas completas".
3. En Variables, completa SOLO el valor LOCAL de c360_password con tu contraseña.
   c360_usuario ya contiene isaidemo; puedes cambiarlo si usarás otra cuenta.
   La URL c360_base_url ya apunta al servicio real de Render, sin barra final.
4. Usa "No Environment" para evitar variables ajenas que sustituyan los valores.
   No compartas/sincronices el valor privado ni exportes una copia con contraseña
   o JWT reales. El JSON entregado tiene ambos campos vacíos.
5. Ejecuta por orden T01, T02, etc., con Send; o usa Run collection con UNA
   iteración, en el orden de las carpetas y con timeout de al menos 60000 ms.
6. La colección guarda JWT, IDs, ETag y líneas base automáticamente. No tienes
   que copiar el access_token. Las pruebas usan Bearer y deshabilitan cookies.
7. Para capturar la prueba de privacidad en Firestore, haz la ejecución manual
   y detente después de T19. Copia el ID de c360_id_privacidad, revísalo en la
   consola de Firestore y continúa con el resto; al final se borrará ese ID.

REGLAS DE EJECUCIÓN
- Haz una prueba a la vez y evita que otra persona escriba interacciones mientras
  comparas las líneas base; si ocurre, los cambios de totales pueden ser legítimos.
- En Test Results, una prueba verde significa que coincidió con lo esperado.
  HTTP 401, 403, 404, 409 y 422 son CORRECTOS en sus casos de rechazo.
- Si falla una prueba positiva, detente y comparte el código HTTP y el detalle
  sin credenciales. Una solicitud marcada Skipped no cuenta como aprobada:
  indica que falta un prerrequisito y debes ejecutar los pasos previos.
- GET y DELETE no llevan body. Logout no lleva body. POST/PUT/PATCH con datos
  usan Body -> raw -> JSON, ya configurado en cada petición.
- No cambies manualmente c360_id_prueba ni c360_id_privacidad por IDs importados.
  Son exclusivamente los dos registros de demostración creados por la colección.
- Si un ID aleatorio choca con otro existente, el alta responde 409 sin sobrescribir.
  Reintenta el alta; las modificaciones solo se habilitan después de un 201.
- Si interrumpes el recorrido después de las altas, vuelve a T04 si venció el JWT
  y ejecuta la carpeta 07 para limpiar SOLO esos registros propios. Si la versión
  del documento cambió, vuelve a T13 para leer su ETag antes de eliminarlo.
- Al repetir el recorrido completo, limpia primero la ejecución anterior y vuelve
  a establecer las líneas base en T10 y T11. No regeneres ni recargues el ETL.

ESTRUCTURA DE PAYLOADS
El body visible de cada petición ya trae los campos que usa ese endpoint.

POST /auth/login: usuario y password. El pre-request serializa ambos para que
comillas o barras dentro de la contraseña no rompan el JSON.

POST /api/interacciones: id_interaccion, id_usuario, timestamp con zona,
canal, tipo, texto (salvo reacción), tema, sentimiento, idioma, dispositivo,
reacciones_recibidas, etiquetas y ubicación cuando corresponda.
longitud_texto se puede omitir: la calcula el servidor. La prueba de longitud
inválida la envía expresamente para comprobar el rechazo.

PUT /api/interacciones/{id}: envía el documento completo con todos los campos
obligatorios; id_interaccion va en la ruta, no en el body. ubicacion:null elimina
la ubicación de esa interacción. No se cambia el consentimiento del usuario.

PATCH /api/interacciones/{id}: envía solo los campos a cambiar. No admite body
vacío; solo texto y ubicacion pueden ser null, y texto:null requiere tipo=reaccion.
Si cambias texto y no envías longitud_texto, se recalcula.

Los IDs cumplen U + 6 dígitos e I + 7 dígitos. Los nuevos ejemplos usan I9xxxxxx
para distinguirlos del conjunto importado; siguen siendo datos de demostración.
sentimiento: -1 a 1; contadores: enteros no negativos (no booleanos);
tipos: mensaje, comentario, reaccion, respuesta_encuesta, rsvp_evento.

CRITERIOS PARA CERRAR LA FASE 4
[ ] Funcionan las consultas reales de usuarios en Turso e interacciones en Firestore.
[ ] Hay evidencia de altas 201, duplicados 409, cambios 200 y bajas 204/404.
[ ] Los payloads inválidos devuelven 422 y no alteran el registro propio.
[ ] Las rutas privadas rechazan solicitudes sin sesión o con token inválido.
[ ] Las referencias a usuarios inexistentes son rechazadas.
[ ] La prueba de privacidad no devuelve ubicación y el documento real de Firestore
    tampoco contiene el campo ubicacion. No basta solo con mirar la respuesta GET,
    porque la API también filtra geografía en sus lecturas.
[ ] La analítica refleja altas, PATCH, PUT y bajas; al limpiar vuelve a la línea base.
[ ] El padrón histórico permanece igual; no se incrementan sus contadores del CSV.
[ ] Los dos documentos de prueba quedaron eliminados; no se tocó el CSV original.
[ ] El logout invalida el JWT. La cuenta puede volver a entrar después.

CAPTURAS

independientes de los números Txx: 01_nombre_descriptivo.png, 02_..., etc.

privacidad (API y documento Firestore); PATCH y PUT; cambios en la analítica;
eliminación y 404; restauración de totales; JWT revocado.
Oculta Authorization, Cookies y cualquier JWT de la respuesta del login.
